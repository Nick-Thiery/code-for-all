You will hit one. That's normal: a <Term>merge conflict</Term> doesn't mean you broke anything.

## Why it happens

This tends to happen when two <Term term="branch">branches</Term> change the **same line**. Instead of assuming which is correct, Git stops and asks you.

If two branches change *different* lines, or different files, Git joins them together by itself. A conflict only happens when the same line of the same file was changed in two different ways ([GitHub: about merge conflicts](https://docs.github.com/en/pull-requests/reference/merge-conflicts)).

Think of two friends editing the same shared shopping list. One changes "6 eggs" to "12 eggs". The other changes "6 eggs" to "no eggs". Nobody can just add both changes together. Someone has to decide. That's a merge conflict.

## What it looks like

Say main and your branch, alex-keyboard, both changed the Wordle page title. Git shows you this:

```html
<<<<<<< HEAD
<h1>Wordle by Team 3</h1>
=======
<h1>Team 3 Wordle</h1>
>>>>>>> alex-keyboard
```

Git shows you both versions, between three <Term def="lines Git adds to a file to show where a conflict starts, where its two versions meet, and where it ends.">marker lines</Term>. Which version is on top depends on which branch you're on when the branches are joined ([how Git shows conflicts](https://git-scm.com/docs/git-merge#_how_conflicts_are_presented)):

- **The top part**, between `<<<<<<<` and `=======`, belongs to the branch you're on. Git calls it <Term def="Git's name for the branch you're on right now.">HEAD</Term>.
- **The bottom part**, between `=======` and `>>>>>>>`, comes from the branch being merged in. Its name is on the last line.

In this example, you're on main and merging alex-keyboard into it. That's what you'd see if you merged alex-keyboard into main on your computer, for example with Claude Code. So:

- The top version, after `<<<<<<< HEAD`, is main's: "Wordle by Team 3".
- The bottom version, before `>>>>>>> alex-keyboard`, is your branch's: "Team 3 Wordle".

### On GitHub, it's the other way round

You'll usually fix conflicts on GitHub, with the **Resolve conflicts** button on a pull request. GitHub does it the other way: it merges main into your branch. So your branch is on top, and main is at the bottom ([GitHub Skills](https://github.com/skills/resolve-merge-conflicts)):

```html
<<<<<<< alex-keyboard
<h1>Team 3 Wordle</h1>
=======
<h1>Wordle by Team 3</h1>
>>>>>>> main
```

Same conflict, same two titles. The rule hasn't changed: the top belongs to the branch you're on, and the last line names the one coming in. When in doubt, read the names on the first and last marker lines.

## How to fix it

1. Keep the version you want, or combine both versions of code.
2. Delete the `<<<`, `===` and `>>>` marker lines.
3. Commit again.

For example, in the Wordle conflict, to keep main's title, those five lines become one:

```html
<h1>Wordle by Team 3</h1>
```

Sometimes you want both. In the editor picture above, main added four links and develop added two. Neither is wrong, so combining both would keep all six links, with the three marker lines deleted.

Before you commit, check that no marker lines are left anywhere in the file. A leftover marker line can show up on your page, or stop your code working.

## The escape hatch

An escape hatch is the easy way out. Paste the entire block of code into Claude Code, then say:

```prompt title="The escape hatch"
I have a merge conflict in <name of the file>. Please help me resolve it and keep all features working.
```

Replace `<name of the file>` with the name of the file that has the conflict.

If Claude Code is already working in your project, you don't even need to paste the block. Claude Code's own guide suggests asking ([Claude Code quickstart](https://code.claude.com/docs/en/quickstart)):

```prompt title="Example: from Claude Code's guide"
help me resolve merge conflicts
```

Claude Code can find the conflict and suggest a fix. Read what it chose before you accept it: you decide which version wins.
